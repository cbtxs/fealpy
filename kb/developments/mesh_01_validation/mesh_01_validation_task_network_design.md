# FEALPy | Development Task | 新网格模块稳定化验证 | Task Network 设计

- **任务编号**：new_mesh_01_validation
- **任务类型**：Development Task
- **设计目标**：把“审架构、做算例、做新网格类型与验证”拆分为可并行、可交付、可复核的任务网络

## 一、网络设计原则

本任务采用“每人独立走一条完整路径”的组织方式。

- 每位成员先独立完成 A：架构审查与问题清单。
- 随后每位成员二选一，走 A->B->D 或 A->C->D 的完整路径。
- 不同人的路径之间不设置前后依赖，不要求先后接力，也不要求共用中间实现成果。
- D 只验证本路径上的产物，不承担跨路径整合，不作为多人共用的中央收口点。

## 二、并行与通信纪律

- 每位成员只对自己选择的路径负责到底，不与其他成员形成串联依赖。
- 交接只发生在个人路径内部，交接物以文档或脚本为准，不以口头共识为准。
- 阶段内如无阻塞，成员自行推进；如有阻塞，只围绕自己路径的阻塞点发起定向提问，不展开跨路径讨论。
- A、B、C、D 都是个人路径中的节点，不是多人共享的公共接力站。
- 详细、完整的测试和自动测试系统建设不放在本任务，留给后续专业测试阶段。

## 三、建议的任务节点

### 节点 A：架构审查与问题清单

- 目标：读文档、读代码、形成问题清单。
- 负责人：每位成员都要独立完成。
- 输出：架构学习笔记、问题列表、风险判断、建议方向。
- 依赖：无。
- 交接方式：A 只向同一条个人路径内部的 B 或 C 提供前置判断，不向其他成员或其他路径共享中间结论。

### 节点 B：新架构算例实现

- 目标：选取一个研究主线，完整使用新网格模块跑通算例。
- 路径：A -> B -> D。
- 负责人：选择该路径的成员本人。
- 输出：可运行脚本、运行说明、结果说明、必要的网格辅助算法。
- 依赖：仅依赖该成员自己完成的 A。
- 交接方式：B 的产物只进入该成员自己的 D，不进入其他成员路径。

### 节点 C：新网格类型实现

- 目标：实现一种新的网格类型或新的实体组合方式。
- 路径：A -> C -> D。
- 负责人：选择该路径的成员本人。
- 输出：schema / storage / view 或相关补充模块、示例数据、构造入口。
- 依赖：仅依赖该成员自己完成的 A。
- 交接方式：C 的产物只进入该成员自己的 D，不进入其他成员路径。

### 节点 D：验证与测试收口

- 目标：验证该成员自己路径上的算例或网格类型产物，形成阶段性证据。
- 负责人：选择该路径的成员本人。
- 输出：验证说明、结果记录、阶段性证据。
- 依赖：仅依赖该成员自己路径上的 B 或 C 产物。
- 交接方式：只对自己路径内的产物做验证，不承担跨路径汇总。

## 四、推荐关系结构

- 每位成员的完整路径都是 A->B->D 或 A->C->D，路径之间互不依赖。
- A、B、C、D 在这里不是公共池中的共享节点，而是每位成员各自路径中的连续阶段。
- B 与 C 是路径分叉，不是跨人协作关系。
- 若团队人数为 3~4 人，建议至少覆盖多个路径实例，以拓宽网格类型和算例验证面，但不要求成员之间串联完成。

## 五、路径映射建议

- 每位成员在启动时先独立完成 A。
- 随后根据自身研究主线选择路径 A->B->D 或 A->C->D。
- 建议在 3~4 人配置下，尽量让一部分成员走算例路径，一部分成员走网格类型路径，以扩大验证覆盖面。
- 不设跨人角色映射，不设中央验证负责人，不设路径间接力责任。

## 六、网络收口要求

每位成员最终收口时至少应回答以下问题：

- 新网格模块最值得保留的结构是什么
- 当前实现最不合理的地方是什么
- 哪个算例最能证明新架构可用
- 哪种新网格类型最能暴露架构边界
- 这些验证结果是否足以支撑后续更大规模协作
